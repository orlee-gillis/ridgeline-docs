This work sample covers three marketing pieces for the Unused Access feature. For each one, the AI
draft appears exactly as it was generated, untouched, next to my edited version. A summary under
each pair explains what I changed and why, so the edits show the editorial judgment behind them.

To see the complete pieces, open the Claude Design files:
[the unedited AI draft](https://claude.ai/artifact/FWWzy7RV4wbF5x7R5k4cmt) and
[my edited version](https://claude.ai/artifact/1iUNCzwhLgYquPGuAdNz89). Each file holds the landing
page, the blog post and the one-pager.

:::info[About this product]

Ridgeline is a fictional cloud security product that I created for this portfolio. Nothing described
here is a real product. Unused Access is one of its features. It finds connected integrations,
including service accounts, that hold access they were granted but never use, and recommends
narrower access that keeps each integration working. Findings are ordered by how much of the
environment each integration can reach, so security teams can decide where to reduce access first.
For the product documentation, see [Unused Access report](unused-access-report.md).

:::

## The three pieces

Each piece has its own page, with the AI draft and my edit side by side and every change listed
with the text before, the text after, and why it changed.

- [Landing page](marketing-work-sample/landing-page.mdx): 11 text changes. The edit leads with the
  risk and what the reader gets, replaces abstract phrases with concrete ones, drops product
  jargon, and closes by inviting readers to learn more.
- [Blog post](marketing-work-sample/blog-post.mdx): 16 changes, including five added product
  screenshots. The edit explains why unused permissions matter, follows one engineer's example
  through two sections, and uses plain terms throughout.
- [One-pager](marketing-work-sample/one-pager.mdx): 10 text changes. The edit opens with the risk,
  gives vague references such as "it" and "excessive access" a clear subject, and uses the
  same wording as the landing page and blog post.

## How this work sample was made

### How it was published

I edited the three pieces in Claude Design, then used Claude Code to turn my edits into these pages.
Claude Code wrote the Markdown, added the screenshots, and opened a pull request in GitHub. The
checks in the next section run on every pull request. When I merge it, GitHub publishes the
Docusaurus site to GitHub Pages.

### How it was checked before it was published

I built an automated review process for this site with Claude. Every change goes through a pull
request, and the site is published when the pull request is merged. I merge only after the checks
pass. The pull requests that published this work sample ran these checks:

- **Prose style, Markdown structure, links and a full site build.** These are rule-based checks
  with no AI involved. A style error, a broken link or a failed build turns the check red.
- **An advisory review by Claude.** It reads the changed pages and posts a comment on claims that
  look unsourced, terms used inconsistently, or a page that drifted from its purpose. It never
  fails the build. A person reads the comment and decides.
- **Genre checks by Claude.** Pages that declare a document type are checked against a written
  checklist for that type. These work-sample pages declare no type, so the other checks cover them.

For how the checks are split and why, see [CI gates](meta/ci-gates.md).

### Claude skills I used for the marketing content

I built these skills and used them to keep the landing page, blog post and one-pager accurate and
consistent with the product:

- **unused-access-expert:** supplies the sourced facts and approved terms for Unused Access, so
  every claim in the three pieces matches the product.
- **ridgeline-doc-auditor:** flags claims without a source, undefined terms and wording that
  differs between pieces, so the pieces don't contradict each other.
- **documentation-orchestrator:** decides which checks a feature needs and runs them in order, so
  the three pieces start from a vetted description of the feature.
- **user-guide-validator:** checks that the task steps are complete and in order, which is what the
  landing page's three steps, the blog's "where to start" and the one-pager's steps rely on.
- **mcp-tool-reference-validator:** checks that a feature's tool details (inputs, outputs and error
  cases) are complete and verified, so capability claims rest on a full specification.
- **llm-docs-validator:** checks that a feature's scope, limits and decision logic are stated
  explicitly, so what Unused Access does and doesn't do is unambiguous in all three pieces.

I also built three skills for other documentation work: ridgeline-doc-writer,
documentation-input-validator and api-reference-validator.
