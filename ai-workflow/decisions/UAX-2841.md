## The sentence "Scope is never narrowed" in `about-the-access-tab.md`

A grant applies at one level of the scope ladder: **Organization**, **Workspace group**, **Workspace**,
**Project**, or **Resource**. Moving a grant to a lower level means it covers fewer resources than before.

| | Before | After this release |
| --- | --- | --- |
| Ridgeline's platform permissions | Read grants and activity logs | Read, plus change role definitions and the grants that attach roles - granted at connection time, or by re-consenting an existing connection |
| The recommendation | Applies at the grant's existing scope level, and cannot be altered | Applies at the same level, but the reader can select a lower level at the confirmation step |
| Is "Scope is never narrowed" accurate | Yes | Only for the recommendation, not for the change the reader applies |

**Files that state scope is never narrowed**

| File | Change required |

| `about-the-access-tab.md` | Reword "Scope is never narrowed. The replacement applies at the grant's original scope." Do not delete it - it is still accurate for the recommendation |
| Unused Access overview | Qualify "no additional platform permissions" - accurate for reading, not for writing |
| `style-guide.md`, publish-readiness checklist | The line "No remediation is described as narrowing scope or changing team membership" would fail a page that documents the reader's scope selection |
| `knowledge-base.md` §9, invariant 1 | States that no recommendation ever narrows scope and that documentation must never describe one doing so |

## Excluded from the draft

The assignee's comment on the story states that the write API accepts an array of grants while the
interface submits one. Documenting it would announce bulk apply one release before it ships.

**My action items: duplicate copies of `glossary.md` are not compared in CI**

| | |
| --- | --- |
| Issue | Two copies of `glossary.md`, one in each skill folder, so that each folder contains every file the skill references. No CI step compares them |
| Effect | An edit to one file is not propagated to the other, and a page drafted against the older copy follows outdated terminology rules without raising an error |
| Resolution | A CI step that runs `diff` on the two files. `diff` returns exit code 1 when they are not identical, which fails the step and blocks the merge. Both copies stay in place |
