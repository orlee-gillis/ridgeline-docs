# Interactive Questions for Documentation Type Selection

Used by the orchestrator when no configuration file exists (`.claude/documentation-config.json`).

---

## Question 1: Programmatic Interface

**Question:**
```
Does this feature expose an API, tool interface, microservice, SDK function, or other 
programmatic interface that code or other systems can call?
```

**Purpose:** Determines if MCP tool documentation is needed.

**Answer "yes" if:**
- Users write code to call this feature
- Other services/microservices call this feature
- The feature is a tool definition with parameters and return values
- External systems can invoke this feature programmatically
- There's a REST API, gRPC endpoint, SDK method, or similar interface

**Examples of "yes":**
- An API endpoint for checking tool access: `GET /api/get_unauthorized_access`
- An SDK function: `client.detect_unauthorized_access(agent_id, days_back)`
- A tool definition in a workflow system
- A database query interface
- A microservice that other services depend on

**Examples of "no":**
- A background batch process with no external interface
- An internal algorithm that users don't interact with directly
- An infrastructure component (load balancer, message queue, etc.)
- A policy or rule that doesn't have user/code interaction points

**If yes →** Add `mcp-tools` to `documentation_types`

---

## Question 2: User-Facing Workflows

**Question:**
```
Do end users (not just developers or admins, but the actual users of your system) 
interact with this feature directly to accomplish tasks?
```

**Purpose:** Determines if user guide documentation is needed.

**Answer "yes" if:**
- Non-technical users use this feature via a UI or CLI
- End users perform multi-step tasks involving this feature
- Users make decisions while using the feature (choosing between options, interpreting results)
- A guide explaining "how to accomplish X using this feature" would be useful
- Users need troubleshooting help if something goes wrong

**Examples of "yes":**
- A security engineer reviews unauthorized access findings in a dashboard
- An end user uploads a file via a web interface
- An admin configures settings in a console
- A data analyst interprets reports generated by the system

**Examples of "no":**
- Only developers call the API directly
- Only internal ops teams run the system (no external users)
- The feature is invisible to end users (works behind the scenes)
- There are no user decisions or workflows (it just runs automatically)

**If yes →** Add `user-guide` to `documentation_types`

---

## Question 3: AI/LLM Reasoning

**Question:**
```
Might AI systems (such as Claude, autonomous agents, or LLM-based tools) 
need to understand and reason about this feature to accomplish their goals?
```

**Purpose:** Determines if LLM-ingestible documentation is needed.

**Answer "yes" if:**
- You want Claude or other AI assistants to be aware of this feature
- Autonomous agents might need to invoke this feature
- Claude's context window should include knowledge about this feature
- An LLM might need to decide whether to use this feature in a workflow
- You're building an AI agent that should understand this capability

**Examples of "yes":**
- A security AI agent should know how to query unauthorized access findings
- Claude Code should know how to use this API when helping users
- An autonomous workflow executor needs to understand this feature's capabilities
- LLM-based decision-making depends on understanding this feature

**Examples of "no":**
- Only humans use this; AI doesn't need to know about it
- This is an internal implementation detail not relevant to AI reasoning
- Users ask Claude for help with the feature, but Claude doesn't directly use it
- The feature is too specialized or domain-specific for LLM use

**If yes →** Add `llm-docs` to `documentation_types`

## Common Patterns

### Pattern 1: API-Only (Developer Tool)

**Typical answers:**
- Q1 (Programmatic interface): **YES**
- Q2 (User workflows): **NO**
- Q3 (AI reasoning): Maybe

**Result:** `["mcp-tools"]` or `["mcp-tools", "llm-docs"]`

**Example:** A Python SDK for calling an analytics service. Developers use it directly. No end-user UI. Possibly useful for LLM context.

### Pattern 2: UI-First (End-User Feature)

**Typical answers:**
- Q1 (Programmatic interface): Maybe
- Q2 (User workflows): **YES**
- Q3 (AI reasoning): Maybe

**Result:** `["user-guide"]` or `["user-guide", "llm-docs"]` or `["mcp-tools", "user-guide"]`

**Example:** A dashboard for reviewing findings. End users interact with the UI. Might also have an API for power users. Maybe useful for AI agents to understand.

### Pattern 3: Full Stack (API + UI + AI)

**Typical answers:**
- Q1 (Programmatic interface): **YES**
- Q2 (User workflows): **YES**
- Q3 (AI reasoning): **YES**

**Result:** `["mcp-tools", "user-guide", "llm-docs"]`

**Example:** A comprehensive feature with:
- REST API for developers
- Web UI for end users
- Documented in Claude's context for autonomous workflows

### Pattern 4: Internal / Infrastructure

**Typical answers:**
- Q1 (Programmatic interface): NO
- Q2 (User workflows): NO
- Q3 (AI reasoning): NO

**Result:** `[]` (Don't use documentation orchestrator; this feature doesn't need external documentation)

**Example:** An internal optimization algorithm, database schema, or infrastructure component. Only documented for developers maintaining the codebase, not external users.

## Decision Tree (Visual)

```
Is there a programmatic interface?
├─ YES → Need MCP tool docs
└─ NO  → Skip MCP tool docs

Do end users interact with this directly?
├─ YES → Need user guide docs
└─ NO  → Skip user guide docs

Should AI systems understand this?
├─ YES → Need LLM docs
└─ NO  → Skip LLM docs

Result: Run validators for selected types
```

## How Answers Map to Config

| Q1 | Q2 | Q3 | Recommended Config |
|---|---|---|---|
| YES | NO | NO | `["mcp-tools"]` |
| YES | NO | YES | `["mcp-tools", "llm-docs"]` |
| YES | YES | NO | `["mcp-tools", "user-guide"]` |
| YES | YES | YES | `["mcp-tools", "user-guide", "llm-docs"]` |
| NO | YES | NO | `["user-guide"]` |
| NO | YES | YES | `["user-guide", "llm-docs"]` |
| NO | NO | YES | `["llm-docs"]` |
| NO | NO | NO | (No docs needed; skip orchestrator) |

## Tips for Answering

**Be honest, not aspirational:**
- If end users *could* use this but don't, answer NO to Q2
- If developers *might* write code to use this but don't, answer NO to Q1
- If AI *could* be useful but you don't have a use case yet, answer NO to Q3

**Think about the MVP (minimum viable product):**
- For a new feature, answer based on what you're shipping NOW
- You can always update the config later as the feature evolves
- Phase 1 might need only Q1 (API docs), Phase 2 adds Q2 (user guide), Phase 3 adds Q3 (LLM docs)

**When in doubt, err toward "yes":**
- Extra documentation is better than missing documentation
- You can choose not to generate certain types later
- The orchestrator offers to pick which drafts to generate
